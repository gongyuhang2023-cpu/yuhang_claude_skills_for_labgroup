# 服务器硬事实 — 推荐时必须知道的约束

> 这些是让推荐"正确"的底层事实。具体数字（池子大小/floor）以 `config.json` 为准；
> 下面的机制对这类"统一内存单 GPU + Slurm"部署是通用的。

## 内存架构：一个池子
- CPU 和 GPU **共用同一个统一内存池**。没有独立显存框；`nvidia-smi` 显存显示 N/A，
  看统一池用量看 `free`。
- 预算（2026-07-20 起）：物理 124,609 MB → `RealMemory=118000`（94.7%，师兄要求不超 95%）
  → 减 `MemSpecLimit=4096`（守护进程保命，免疫 OOM）→ **用户可申请上限 113,904 MB**。
- 调度按**预留**记账，不按物理占用。判断"还能塞多少"用 `RealMemory − AllocMem`，
  **别信物理 FreeMem**（GPU 作业预留 96G 只用 60G 时物理看着空，但调度不进）。

## GPU：串行，一次一个
- 只有 1 块 GPU，**无 MIG**，硬约束：`gres=gpu:1` → 同时只跑一个 GPU 作业。
- 所以两个 GPU 作业必然排队；GPU 作业与 CPU 作业可并行（只要内存账算得下）。

## ★ cgroup 到底管不管得住 CUDA —— 2026-07-19 本机实测，别再凭直觉推测

三条路径行为**不同**，这是本机最重要的事实：

| 分配方式 | 限额 4G 去分配 8G 的结果 | cgroup 记账 | 实际吃掉 |
|---|---|---|---|
| 普通 CPU 内存（malloc） | **被 OOM 杀** ✓ 管得住 | 准确 | — |
| `cudaMallocManaged`（统一内存） | **被 OOM 杀** ✓ 管得住 | 准确 | — |
| **`cudaMalloc`（设备内存）** | **活到结束** ✗ **管不住** | **0.08 GB** | **8.37 GB** |

**PyTorch 默认走 `cudaMalloc`** → 我们实际会跑的 GPU 程序基本都在"管不住"这条路上。
推论：**GPU 作业的 `--mem` 只约束得了它的主机侧内存，约束不了显存。**

## ★ 但显存能被"看见" —— 2026-07-20 实测

`nvidia-smi --query-compute-apps=pid,used_gpu_memory` **在 GB10 上是准的**
（整卡的 `--query-gpu=memory.used` 才是 `[N/A]`，两者别搞混）。
配合 `/proc/<pid>/cgroup` 里的 `job_<N>` 就能把显存**精确归到作业头上** ——
cgroup 记账看不见的，它看得见。实测 8 GB 分配 → 报 8362 MiB。

由此：`--mem` 对 GPU 作业是一份**申报**。它的分量不来自 cgroup（管不住），
而来自 **`spark-memguard` 按"实际占用 vs 申报量"对账**：内存 ≥88% 时
冻结超出自己申报最多的那个作业（冻结≠杀掉，可解冻续跑）。

## 关键不对称：GPU 侧宁可多报
- **多报 GPU 内存 = 便宜**：GPU 串行，多报只是少给并行的小 CPU 活腾空间。
- **少报 GPU 内存 = 危险，且现在会直接反噬自己**：显存超支不受 cgroup 约束、
  会吃进池子空闲；若此时有并行 CPU 作业、总量超顶 → 整机内存耗尽（已知死机模式）。
  而且申报低于实际用量 = **把自己排到第一个被 memguard 冻结的位置**。
- 结论：GPU 作业的 `--mem` 报成"真实峰值 + 余量"，宁高勿低；不确定就**别写**
  （走 96G 默认跑一趟，采样器会记下真实峰值，下次照着填）。

## 提交规则（lua，2026-07-20 起）
- **GPU 作业**：★**写了 `--mem` 就按你写的给**（不再一律抬到 floor）。
  - 不写 → 兜底 `GPU_MEM_FLOOR_MB = 96000`
  - 写了但 < 4096 → 抬到 4096（CUDA 上下文本身要 ~1G）
  - 只写 `--mem-per-cpu` → 不接受这种形式，退回 96000 默认
  - **旧行为（写了也抬到 96G）已废除**：那导致只要 8G 的小推理也得等 96G 空出来。
- **纯 CPU 作业**：**不写 `--mem` 会被直接拒绝提交**（`--mem=0` 同样拒绝）。
  理由：`DefMemPerNode=UNLIMITED`，不写等于把整机内存记在自己名下，别人就提交不了。
  **拦在提交阶段，而不是跑起来再杀。** `--mem-per-cpu` 也算写了，放行。
  → **所以给 CPU 作业出推荐时，`--mem` 是必填项，不能省略。**

## cgroup 兜底：估错只崩自己
- `ConstrainRAMSpace=yes`：每个作业的**主机侧内存**被硬卡在申报的 `--mem`。
- CPU 作业估小了 → 超限时**只有它自己被 OOM 杀**，别人和系统安然无恙、可重交。
- ★ **swap 已于 2026-07-20 关闭**。此前作业能靠换页悄悄超出 `--mem`（实测：限额 4G 的
  进程成功分配 6G）；关掉后 `--mem` **才真正有约束力**（实测：申请 2G 用 5G → `OUT_OF_MEMORY`）。
  关 swap 的另一个理由：这台机器内存吃紧时 swap 抖动会把"任务失败"放大成"整机僵死"。
- 所以推荐可以大胆给（估错代价低），但仍要诚实标置信度。
- ★ 注意：以上只覆盖**走队列提交**的作业。**裸跑（不经 sbatch/srun、直接 `python xxx.py`）的
  进程不在任何 `job_<N>` cgroup 里** → `spark-memguard` 归因不到它（`job_of_pid` 返回 None），
  既不受它约束、也不被它保护；内存吃紧时系统反而会去冻**守规矩走队列**的作业。再加上 sacct
  不留痕、会抢显存撞崩别人的卡 —— 所以**任何 GPU/重活都必须走队列**（见 SKILL.md 顶部红线）。
  这是硬要求，不是建议。

## 关键服务已免疫 OOM
`ssh` / `tailscaled` / `slurmctld` / `slurmdbd` 均设了 `OOMScoreAdjust=-1000` + `MemoryMin`。
意义：内存被压满时这几个不会被杀 → **仍可远程登录处理，不必到现场按电源**。
（但内核级卡死的情况救不了，社区有卡死 1h47m 的记录——所以仍要从源头避免吃满。）

## 其它约束
- 分区就一个：`main`（默认）。任务时间上限 **14 天**（超了交不上）。
- 每人磁盘配额（软 500G / 硬 700G）；`quota -s` 看用量，超了写不进。
- 公平调度（fairshare）：多跑的人会自动给用得少的人让位；账户记账在 `sacct`。

## sacct 历史的边界
- `sacct` 的 `MaxRSS` = **主机侧（CPU）内存峰值**，可靠。
- **不含 GPU 显存峰值**（sacct 抓不到）。所以 GPU 作业的内存历史目前是空白，
  靠"宁可多报 + 标定"补；这是 MVP 的已知局限，未来用 profiled run 自建 GPU 峰值日志。
