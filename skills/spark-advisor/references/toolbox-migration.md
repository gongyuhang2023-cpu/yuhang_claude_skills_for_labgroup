# 将工具箱调用迁入项目环境

每位成员的 AI 只处理该成员自己的项目、脚本和作业。用户指定单个项目时，按该项目的实际启动脚本、工作目录、软链引用和相关作业核对。Spark 扫描会同时返回个人软链清单，用来判断引用。成员全量排查和最终报告用于已获授权的全量迁移。排队和运行中的作业继续按原计划执行，其依赖的脚本、锁、环境和输入路径等作业结束后再改。

课题工具要随项目锁定，版本和依赖才能随代码复现。管理员收到全部成员的迁移报告后，会撤掉除公共 R 以外的工具箱。迁移时一起处理指向工具箱的个人软链，避免工具箱撤除后调用失效。

逐个项目让用户决定怎么处理。迁移要改脚本和试跑。明确不迁的项目记录用户决定及理由。需要保存环境记忆但暂时不用的项目可选「冻结」，见第 6 节。

## 1. 收集调用位置

先读 `rules`，确认本人在 Spark 上的项目、家目录里的独立脚本和近期作业目录（如 `~/Workspace/tmp`）。先核对实际存在的路径，再一起传入。下面以已有的项目和作业目录为例。家目录的独立脚本用实际文件或所在目录补扫。

```bash
python scripts/advise.py software scan '~/Workspace/Projects' '~/Workspace/tmp'
```

输出 JSON 的 `hits` 中，每处有 `file`、`line`、`command`、`tool`、`recipe`。`recipe_source` 标出所用目录的来源。`files_scanned` 统计识别到的脚本，`skipped` 列出需要人工看的跳过项（R 脚本、软链文件）和原因；其余不是脚本的文件只在 `skipped_other` 里给出数量和少量示例路径。对于 `.R` 要人工查看 `system()` 和 `system2()`。从目录扫时跳过的缓存目录无需逐个核对。扫描覆盖 shell 脚本、sbatch、Snakefile、Nextflow 和 Python 中可静态识别的外部调用。扫描自动排除被 Spark 系统命令盖住的裸命令。对剩余裸命令，核查原作业的 PATH 和激活步骤，区分已锁入项目的命令和工具箱调用。显式工具箱路径照常计入。`tool` 和 `recipe` 为 `null` 的条目逐项确认。先处理 `errors` 中的路径或解析问题，再人工查看变量拼出的命令、包装脚本和 here-doc 内的动态执行。

扫描跳过有 `conda-meta/` 或 `pyvenv.cfg` 的嵌入环境及常见第三方代码目录。`skipped_envs` 给出环境数量和最多 20 个示例路径。对这些环境仍检查 `bin/` 指向工具箱的软链，命中时列入 `symlinks`，来源为 `embedded-env`。

在 Spark 上，`symlinks` 还包括家目录的整环境软链（包括 `~/.pixi/envs`）、混合 conda/mamba 环境 `bin/` 和 `~/.local/bin`、`~/bin` 的工具箱软链。也会检查 `/opt/bio/var/replaced/manifest.tsv` 里本人记录的实际路径，命中时标为 `cleanup-manifest`。同一软链路径只列一次，重合时保留清理清单来源。混合环境可能用 `SHARED-TOOLS.txt` 记录来源。用 `symlink_errors` 核对读不到的目录或清单。扫描只读取文件和链接文本，公共 R 不计入。按第 4 节处理。

`hits` 的 `environment_activation` 项会列出相关环境与软链。核查 `conda activate`、`mamba activate`、`micromamba activate`、`source activate` 和 `conda run -n/-p` 的实际选择，遇到同名环境或相对路径时结合工作目录确认。

结合本人最近的作业核查。在 Spark 上用 `sacct -u "$USER" -S <起始日期> --format=JobID,JobName,State,WorkDir%200` 找到工作目录，再查原脚本和 `logs/*.run.json`（若有）。用 `sacct -u "$USER" -j <作业号> --batch-script` 读取已保存的提交脚本。早期作业可能返回 `NONE`，改查对应目录、脚本和日志。运行记录只识别提交脚本里直接可见的命令。若脚本又调用其他脚本，继续查看下游脚本和相关日志，即使 `tools` 为空也要查。只扫描有权限的个人文件。

## 2. 按项目拟定改动

可把一个项目的写锁、改脚本、构建、试跑、删除软链和清理旧环境写进同一份计划。逐项给出脚本 diff、作业资源与预计时长，以及删除的准确路径。试跑通过和作业结束是清理的前置条件。结果符合计划时逐步执行。[同意规则](../SKILL.md#同意规则)

1. 对每个确认的工具运行 `software find <工具名>`，把 `dependencies`、频道和备注一起核对。配方冲突时，在同一项目拆不同 Pixi feature 和具名环境，分别固定完整频道顺序。兼容工具可合用。公共库继续由 `databases.lock.json` 固定。所需配方有误或目录不可用时，核对 `rules`、重查配方后再迁该工具。库版本不兼容时记录该调用，待确认库与工具组合。
2. 把拟改动的配方、锁和脚本 diff 纳入计划，经同意再改项目文件。若锁须在 Spark 临时目录求解，先展示 manifest diff 和锁的验收范围。锁返回后核对最终 diff 是否符合已同意的计划。检查排队与运行作业，等受影响的作业结束再改。
3. 按 [项目环境流程](project-envs.md) 用 `env build --dir <项目目录> -e <环境>` 逐个预演。确认后加 `--yes --wait` 构建并核对环境就绪。
4. 用 `gen-sbatch --env <项目目录>` 重新生成作业脚本。单环境用 `-e`，多个环境用重复的 `--env-step`。手改时按项目环境文档更新各激活块，保留每个环境的 `# ENV-STORE` 标记，在 `set -u` 下保护激活。生成脚本激活后会从 PATH 移除 `/opt/bio/bin`，调用公共 R 时用 `/opt/bio/bin/Rscript` 或 `/opt/bio/bin/R` 全路径。明确绝对路径的工具箱调用改为项目环境提供的命令，兼容命令按配方核对参数。对照已同意的计划核对脚本最终 diff 后写回。提交前用 `env check` 检查所有标记。
5. Python `subprocess`、Snakemake 的 `shell:` 和 Nextflow 任务用到的工具也要锁定。让启动它们的作业激活对应环境，继承 PATH 的裸命令可保留。脚本若写死工具箱路径、重设 PATH 或自行激活旧环境，把这些引用一并更新。Snakemake、Nextflow 本身也要锁进项目。工作流若为规则或子作业另选环境，按实际启动方式核对每个子任务使用的版本和来源。

## 3. 试跑：用小份输入跑通每一步

试跑脚本用 `gen-sbatch --verify`。它用验证模式登记每个项目环境和通过 `--stage` 使用的数据库缓存。作业仍受清理保护，最近使用时间和使用者保持原记录。手写缓存调用用 `db-cache use --verify KEY`，需要先取库时用 `db-cache fetch --verify KEY`。提交时，暂未缓存的 `--stage` 库以验证模式取回，等库就绪后才交主作业。把仅为试跑构建或取回的环境指纹、仅为试跑取进缓存的数据库 KEY，以及临时恢复的冷数据原路径写入计划和报告，标为「验证用」。先确认这些服务器接口已部署，缺少接口时暂停相应步骤。

每个迁移项目选一个覆盖本次工具调用的代表性作业。参数、数据库固定版本和流程步骤都不变，只把输入缩成能走完每一步的一小份，例如 1 个样本、1 个基因组或几条序列，输出写到新的试跑目录。工具对输入数量有下限时按下限取，例如 Pharokka 的 `-m` 要多条序列。原流程会即时下载输入时，从上次留存的文件里取一小份。脚本写死输出或会重建索引时，在独立试跑目录复用相对路径，保留旧结果及索引。把输入的取法、涉及绝对输出路径的 diff 和试跑资源纳入计划，提交前核对已同意的计划。

跑通的判据：作业正常结束，每个工具以 0 退出；日志里的工具路径来自项目环境，数据库是锁定的版本，没有报错；该工具应交付的主要文件都已生成，例如结果表、注释文件、索引，内容可以没有数据行。不和原来的结果逐个比较。用户另外要求比对时，按用户定的范围比较，比较方法和允许的误差先和用户说定。跑不通时保留原文件，带日志报告，不放宽判据，也不擅自换版本。

### 验证后释放本地副本

试跑结束后，若用户没有安排项目马上继续使用，先预演释放计划中标为「验证用」的环境和数据库缓存。把指纹、KEY、路径和是否可释放列入用户同意的计划，再用 `--yes` 执行。以各接口实际返回的资格和结果为准。已有其他用户近期使用、仍有作业登记或无法核实 NAS 原件时，保留本地副本并记录原因。资格仍满足时，释放请求由下一轮清理处理，最长约一小时。NAS 上的原件保留。

在 Spark 上用下列命令。先代入实际指纹和 KEY，前两行是预演，后两行用于已同意的执行。

```bash
env-store release "$fp"
db-cache release "$key"
env-store release "$fp" --yes
db-cache release "$key" --yes
```

为验证从 NAS 恢复的冷数据目录用 `cleanup park <原目录>` 预演。把确切目录路径、原归档、拟释放空间和可能的核对作业纳入同一份计划。经同意后，用 `cleanup park <原目录> --yes --expect <plan_sha256>` 按本次预演执行。服务器逐文件比对原归档，一致时移走本地副本并写回 `.ON_NAS.txt`。大目录通过 Slurm 核对，拿到作业号时用 `cleanup job` 查看结果。有差异就保留本地副本并报告，验证产物写在恢复目录以外。

## 4. 清理家目录工具箱软链

1. 按 `symlinks` 列出精确的链接路径和目标，包括跳过的嵌入环境 `bin/` 和清理清单中本人的条目。结合 `environment_activation`、脚本和近期作业确认引用。
2. 已迁移的项目先确认试跑跑通。用户选择冻结时，先核对第 6 节约定的记录都已保存。查同一软链是否还被其他项目、排队或运行作业使用，等受影响的使用结束。
3. 给用户看拟删除的清单，经同意后逐项确认 `test -L <路径>` 及 `readlink -- <路径>` 仍与计划相符。相对目标按链接所在目录解释。用 `rm -- <链接路径>` 只删软链本身，路径末尾不加 `/`。保留软链目标和混合环境中的其他文件。计划有变化时重新确认。
4. 在报告中列出处理过的软链路径和相关脚本，仍待迁移或保留的链接写明原因。

## 5. 写报告

将报告写到 **Spark 上本人家目录的 `~/.spark-advisor/reports/toolbox-migration.md`**。首行固定写「状态：已完成」或「状态：未完成」，紧跟下面四节。已迁条目完成试跑，并记录「验证用」的环境、缓存和冷数据的释放、放回或保留结果。用户明确决定不迁，或按第 6 节完成冻结的条目，在最后一节写明用户决定及理由，算作已解决。冻结也写清记录的路径及相关软链的处理结果。仍有待核对或未经用户确认的条目时，填写「状态：未完成」。只记录路径、工具名、版本和试跑结论或原因，数据内容留在原处。

```markdown
状态：未完成

## 改了哪些项目和脚本

## 每个工具锁成的版本

## 试跑结果

## 还剩什么没改及原因
```

## 6. 冻结：不改、不验证

用户明确选「冻结」后，保留现有脚本和作业配置，只在项目内添加环境记忆。冻结流程无需试跑。把要新增的三个文件和拟处理的软链列入计划，经用户同意后执行。

1. 核对脚本中实际用到的工具箱工具和当时的版本，按匹配的推荐配方写 `toolbox-freeze/pixi.toml` 并生成 `toolbox-freeze/pixi.lock`。固定完整依赖和频道，主工具版本须和原工具箱一致。遇到配方冲突时在这份 manifest 内用具名环境分开。缺少确切版本或求解结果不符时，记录缺口并停下确认。`file:///opt/bio/channel` 依赖仍按 `software.md` 的求解流程。冻结配方单独保存，作业脚本保持原样。
2. 写 `toolbox-freeze/README.md`。逐项记录工具箱调用的文件与行号、工具与版本、当前代码提交号。项目没有 Git 时，保存按路径排序的代码文件清单及其 SHA256，排除本次新增的冻结目录。说明以后如何用保存的锁重建，例如给 `env build --dir <Spark 项目>/toolbox-freeze -e <环境>` 预演，获准后构建。以后要继续运行时，另拟把脚本切到锁定环境的计划。
3. 需要 Git 提交时，另行征得用户同意。相关工具箱软链仍按第 4 节处理。告诉用户工具箱撤除后这些路径和旧调用会失效，待日后恢复项目时再接入新建环境。
4. 在报告最后一节注明「冻结」是用户的决定和理由，列出保存的文件与软链处理结果。冻结记录齐全且有关事项处理完毕后，这一项算已解决。

以下是冻结 CheckV 时 `toolbox-freeze/pixi.toml` 的配方示例。

```toml
[workspace]
name = "toolbox-freeze"
channels = ["file:///opt/bio/channel", "conda-forge", "bioconda"]
platforms = ["linux-aarch64"]

[dependencies]
checkv = "==1.1.1"
diamond = "==2.1.8"
python = "==3.12.15"
```
