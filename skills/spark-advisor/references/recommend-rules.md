# 推荐规则 — mem / gres / time 的判断逻辑

> 引擎 `advise.py recommend` 已按这些规则算好 baseline。本文件是你（AI）把 baseline
> 讲成人话、标对置信度、决定排队/现在跑的依据。核心一句：**估不准有 cgroup 兜底，
> 所以求"够好 + 诚实标置信度"，不求神准；GPU 侧宁可多报（串行=多报几乎免费）。**

## 置信度分层（必须标）

| 置信度 | 触发 | 措辞 |
|---|---|---|
| **高** | 历史里有**同尺寸/近尺寸**的同类作业实测 | "抄你上次同尺寸实测 X G + 余量" |
| **中** | 无历史，但用户/AI 给了合理估计（`--mem-guess`） | "按你的估计 + 50% 余量" |
| **低** | 无历史、无估计，或输入规模**超出历史范围** | "粗估/给宽兜底，建议先标定" |

## 内存余量

- CPU 作业：`--mem = 历史 MaxRSS 峰值 × 1.3`（有历史）；或 `用户估计 × 1.5`（无历史）。
- GPU 作业：**宁可多报**。无 GPU 显存历史时给宽默认（≈ `gpu_floor × 1.15`，见 config）。
  - 理由：GPU 串行、一次一个，多报只是少给"顺便捎带的小 CPU 活"腾点空间，代价极小；
    少报才是真风险（CUDA 超支撞并行任务 → OOM）。见 `server-facts.md`。
  - 引擎无论如何 lua 会把 GPU 作业自动兜到 `gpu_floor`（96G）；用户想要更多就照推荐写 `--mem`。

## 时间（--time）

- 有历史：取历史最长 Elapsed × ~1.5。
- 无历史：给宽默认（如 6:00:00），并提醒用户"设成你预期的最长"；上限 14 天（超了作业交不上）。
- 意义：写了 `--time` 作业跑完/超时自动释放 GPU，别让忘取消的作业霸占唯一 GPU。

## 现在跑还是排队

看 `recommendation.run_now` + `server_now`：
- **GPU 作业**：`gpu_job_running=true` → 会排队。告诉用户前面 `pending_count` 个、看正在跑那个的 `time_left` 估等多久。
- **CPU 作业**：`mem_gb > mem_schedulable_gb` → 会排队。否则能和正在跑的 GPU 作业**并行**（轻量 CPU 活尤其）。
- **关键**：判断"还剩多少能跑"看 `mem_schedulable_gb`（= RealMemory − 已预留），**不是物理空闲**。GPU 作业预留了 96G 但只用 60G 时，物理看着空，但只有预留外的部分能调度。

## 给用户的输出模板

```
📊 现状：GPU {空闲/被<user>占着(已跑X,还占YG)}，可调度 {Z}G，队列 {N} 个
📈 历史：{有同尺寸实测 XG / 还没有<tool>记录 → 内存定不准}
💡 推荐（置信度：{高/中/低}）
   --gres={g}  --mem={m}G  --time={t}
   依据：{basis 一句话}
   {若低置信：⭐ 更稳：这趟套个采样，跑完把真实峰值入库，下次就精确}
{若会排队：说明会排在第几、预计等多久，"关机走人轮到自动跑"}
要我 ①{带采样}提交 ②普通提交 ③先不交？   ← 提交前必须问，不自动交
```

## 标定（低置信时主动提议）

没有对应规模的 GPU 显存历史时，最稳是先跑一次**代表性输入**（库筛就跑其中最大的复合物）
并采集真实峰值。GPU 峰值要用**框架自己的计数器**（Boltz 是 PyTorch → `torch.cuda.max_memory_allocated()`），
比外部轮询 `nvidia-smi` 准（不漏瞬时尖峰）。采到的峰值 + 余量就是之后的 `--mem`。
（自动标定 + GPU 峰值入库是 skill 的下一步扩展，当前 MVP 先靠"宁可多报 + cgroup 兜底"。）
