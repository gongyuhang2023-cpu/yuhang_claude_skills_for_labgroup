# 推荐规则 — mem / gres / time 的判断逻辑

> 引擎 `advise.py recommend` 已按这些规则算好 baseline。本文件是你（AI）把 baseline
> 讲成人话、标对置信度、决定排队/现在跑的依据。核心一句：**CPU 作业估不准有 cgroup
> 兜底（只崩自己）；GPU 作业 cgroup 管不住显存，`--mem` 是一份会被 memguard 对账的
> 申报 —— 宁可多报，或干脆不写走默认。**

## 置信度分层（必须标）

| 置信度 | 触发 | 措辞 |
|---|---|---|
| **高** | 历史里有**同尺寸/近尺寸**的同类作业实测 | "抄你上次同尺寸实测 X G + 余量" |
| **中** | 无历史，但用户/AI 给了合理估计（`--mem-guess`） | "按你的估计 + 50% 余量" |
| **低** | 无历史、无估计，或输入规模**超出历史范围** | "粗估/给宽兜底，建议先标定" |

## 内存余量

- CPU 作业：`--mem = 历史 MaxRSS 峰值 × 1.3`（有历史）；或 `用户估计 × 1.5`（无历史）。
- GPU 作业（★2026-07-20 规则已变，`--mem` 写了就会被尊重）：
  - **用户给了估计** → 申报 `估计 × 1.3`。这样别人能和他同时用机器，他也更容易排上队。
  - **没有估计** → **建议不写 `--mem`**，让 lua 兜底给 96G 跑一趟。代价说清楚：
    这一趟别人只剩 ~18G。想让下一趟能精确申报，**在命令里带上自测**（PyTorch 程序结尾打印
    `torch.cuda.max_memory_allocated()/1024**3`）—— 服务器侧虽然也在采（`gpu_proc_samples`），
    但按作业的值取不回来，见下方「标定」段。
  - **必须提醒的后果**：申报低于实际用量 → 内存 ≥88% 时会被 `spark-memguard`
    优先冻结（暂停不是杀掉，可解冻续跑，但会打断）。**往上取整是免费的，往下不是。**
- **CPU 作业的 `--mem` 是必填**：不写会被 lua 直接拒绝提交（见 `server-facts.md`）。

## CPU 核数（--cpus-per-task）—— ★2026-07-23 补齐

**为什么要管**：不写 `--cpus` → 落 Slurm 默认 **1 核/task**，cgroup 把作业钉死在 1 核上。GPU 作业的输入特征化 / MSA 解析 / BLAS 那几步是多线程的，1 核会把它们串行掉（GPU 计算那段不受影响，但预处理更慢）。这是**静默降级、无任何告警**——所以 skill 必须主动兜，别再漏成 1 核。

**逻辑（类比内存的"想要 vs 现在能给"，但有关键区别）**：核是**弹性**的（少给只是慢），内存是**硬地板**（少给直接 OOM）。所以默认**不为了多凑几个核而让 GPU 作业排队**——GPU 才是串行稀缺资源。先看 `server_now.cpu_free / cpu_total` 再定：

| 情形 | 给多少 |
|---|---|
| **GPU 作业** | 默认想给 **4 核**（喂特征化/BLAS），但按空闲收敛 `min(4, cpu_free)`、至少 1。够就 4，不够先给能给的，**绝不为凑核排队**。 |
| **纯 CPU 作业** | 核 = 算力本身，最优值看工具并行度：单线程/串行脚本 1 核；BLAS/sklearn/多进程按需要给。**不硬塞默认**（免得给单线程作业预留一堆核、白占共享池），按工具判断。 |
| **用户显式 `--cpus N`** | 尊重 N；若 `N > cpu_free`，像内存那样提示"会排队等核"。 |

`recommend` 已按上面算好 `recommendation.cpus` + basis，直接把它传给 `gen-sbatch --cpus`。GPU 作业若漏传，`gen-sbatch` 会回一条 `cpus_warning` 提醒——别忽略。

## ★ GPU 显存自限 —— 每个 GPU 作业都要处理

**为什么必须做**：`--mem` 管不住显存（`cudaMalloc` 绕过 cgroup，实测 8 GB 只记 0.08 GB）。
系统层面拦不住失控的 GPU 程序，**唯一的防线是让程序自己给自己设上限**。

**目标状态**：程序撞到自己的上限 → **自己抛错退出**（干净、只影响它自己）
**要避免的**：程序无限申请 → 吃满统一内存池 → **整机僵死、全组作业陪葬、要人到现场重启**

### 各工具怎么设（生成 sbatch 时按工具带上）

| 工具 | 能否自限 | 写法 |
|---|---|---|
| **vLLM** | ✅ 原生支持 | `--gpu-memory-utilization 0.5`（默认 0.9 太高，本机社区实测 >0.8 即临界） |
| **自写 PyTorch 脚本** | ✅ 但需改代码 | 脚本最前面加 `torch.cuda.set_per_process_memory_fraction(0.7)` |
| **Boltz** | ❌ 无直接参数 | 只能从**输入规模**控制：分批跑、降 token 数、减 `--diffusion_samples` |
| **Uni-Dock / Vina** | 一般不需要 | 显存占用小且可预期 |

### 纪律（照做，别含糊）

1. **能设就设**，在 `gen-sbatch` 生成的脚本里直接带上，用户不必知道细节。
2. **不能设就明说**，不要假装安全。原话可以是：
   > "这个工具没有显存上限参数，所以万一它吃超了，**系统层面拦不住**。
   > 建议：① 先用小输入试一次看峰值 ② 跑的时候留意面板 ③ 别在同时段安排大 CPU 作业。"
3. **审用户已有脚本时**：GPU 作业没带上限参数 → **主动指出并给出补法**，这是你的职责，不是可选项。
4. 不确定某工具支不支持时 → **说不确定**，别编参数名。编错了用户会拿到一个报错的脚本。

## 时间（--time）—— ★2026-07-22 起：默认不设限

**不替用户估一个"紧"的 `--time`。** 谁也预估不准运行时长；估短了作业撞到墙钟被
**TIMEOUT 杀掉、整段白跑**（TIMEOUT 是终态，不触发 `--requeue`，不自动续跑），
重跑比"根本不设限"更浪费。而且这台机上估准 `--time` 几乎没收益 —— 它唯一的实际用途
是给 backfill 调度，但 GPU 串行、CPU 活又轻，backfill 省不下什么。用零收益换一个致命
风险，不划算。

**默认行为**：`recommend` 返回 `time=None`，**gen-sbatch 不传 `--time`** → 作业落到分区
默认 `DefaultTime=14 天`（= `MaxTime`，受支持的正规路径，不是钻空子）。

**那"卡死作业空占唯一的卡"谁来防？** —— 服务器端的 **idleguard 闲置看门狗**
（服务器端的闲置看门狗）：一个占着 GPU 的作业若 **GPU 与 CPU 连续 ~1 小时
双静默** → 判定卡死/空转 → 自动回收（先警告、再 `scancel`；交互式豁免；observe/armed
双模式）。这才是对的兜底 —— 它回收"卡住的"作业，不碰"跑得久但在算"的作业；墙钟正好
相反，所以我们不靠墙钟。

**什么时候才写 `--time`**（可选，用户主动）：
- 用户**明确知道**一个安全上限、且想让"万一忘了 `scancel` / 卡住"的作业**早于 idleguard
  的 1 小时**就自动释放 → 传 `--time`。**往大了报**，被杀是唯一坏处，留足余量。
- 传给 `recommend --time <值>` 会被采纳并写进脚本。

**唯一要主动提醒时间的情形**：这活按规模**预计 >14 天才跑得完** → 一次 run 撞天花板也
完不成 → 提醒用户必须 **checkpoint + 分段**，而不是硬提交。其余情况：`--time` 留空。

## 时间（--time）的交互式分支 —— ★2026-09-06：会话必须设限

上面那条「默认不设限」**只管 sbatch**，它成立的前提是 **idleguard 兜底**。
交互式会话（`salloc` / `srun --pty`，`BatchFlag=0`）**不在 idleguard 的射程内**
——`idleguard.py:35` 明写「交互式豁免，只警告不回收」。豁免是对的（人在终端里想事情
不该被打断），但它同时意味着**这条路上没有第二道网**。

三条实测（2026-09-06）：

| 测了什么 | 结果 |
|---|---|
| 普通用户能不能**调大**自己作业的时限 | ❌ `scontrol update TimeLimit` 调大 → `Access/permission denied`；**调小成功** |
| 时限到点时正在跑的活会怎样 | 收到 SIGTERM（srun rc=143），`CANCELLED ... DUE TO TIME LIMIT`，终态 **TIMEOUT**，**不重排不续跑** |
| 会话里每次 `srun` 的启动开销 | 33–61ms（跨 ssh 连接 36–51ms） |

⇒ **风险不对称**：报少了没有补救（不能延长，只能重开→重新排队→机器满时可能进不去）；
报多了唯一坏处是占着，而那个随时 `debug-end` 就能释放。**所以往大了报。**

⇒ 默认 **6 小时**（`DEBUG_DEFAULT_TIME`）。选这个数不只因为"够用"：它短到
**不能拿调试会话当批处理使**，逼着正经长活回到 sbatch 走正常排队。用户主动要更长不拦。

⇒ 剩余跌破 **1/4** 时 `debug-run` / `debug-list` 会在 `warn` 字段里催（`DEBUG_WARN_FRACTION`）。
用比例不用固定值：提前量是留给**重新排队**的，会话越长、要办的事越大，需要的提前量越多。

## 现在跑还是排队

看 `recommendation.run_now` + `server_now`：
- **GPU 作业**：`gpu_job_running=true` → 会排队。告诉用户前面 `pending_count` 个、看正在跑那个的 `time_left` 估等多久。
- **CPU 作业**：`mem_gb > mem_schedulable_gb`（或显式请求的核数 > `cpu_free`）→ 会排队。否则能和正在跑的 GPU 作业**并行**（轻量 CPU 活尤其）。
- **关键**：判断"还剩多少能跑"看 `mem_schedulable_gb`（= RealMemory − 已预留），**不是物理空闲**。GPU 作业预留了 96G 但只用 60G 时，物理看着空，但只有预留外的部分能调度。

## 标定 —— 采集通了，读取没通（★2026-07-20 采集上线）

**采集这一半是通的**：`spark-usage-sampler` 在 GPU 作业运行期间每 5 秒记一次**按作业的
显存占用**（`nvidia-smi --query-compute-apps` → PID → `job_<N>`，落 `gpu_proc_samples` 表）。

**读取这一半是断的**：没有任何命令或接口按作业吐出这个数 —— `spark-usage` 和面板
`/api/usage` 都只给**全机聚合**。按作业的值目前只有管理员直接查
`/var/lib/spark-usage/usage.db` 能拿到（普通用户读不了那个库）。

⇒ 所以低置信时的正确建议是：**这次不写 `--mem`，走 96G 默认跑完** —— 安全、不会因报低
被 memguard 冻。想下次精确申报，得有人把这一趟的实测峰值取出来给你。

⇒ **要自助拿到数，就在程序里自测**：Boltz 这类 PyTorch 程序在结尾打印
`torch.cuda.max_memory_allocated()/1024**3`。这不是锦上添花，是普通用户目前**唯一**能自己
拿到峰值的办法（而且比外部 5 秒轮询更细，抓得到瞬时尖峰）。

### ★ 标定的正确姿势：夹逼，而不是"测个准数"

**从外部观测到的任何数字都是下界，不是峰值。** 两个来源，两种漏法：

| 来源 | 为什么只是下界 |
|---|---|
| 5 秒采样（`gpu_proc_samples`） | 两次采样之间冲高又回落的尖峰拍不到 |
| 被冻结那一趟的读数 | 它是在**越线那一刻**被打断的，之后还会涨 |

采样这条不是理论担忧：2026-08-28 实测 job 200/198（Boltz），`nvidia-smi` 读数在
4.2 ~ 11.3 GiB 之间来回跳了 **9 次** —— 它**会降**。既然会降，就存在没被拍到的更高点。
（对照 job 452 的 ESMFold：3833 个点、一次不降，一路涨到 95.3 就停住。**不同程序行为不同，
不能假设。**）

**上界从哪来：一次「在机器繁忙时正常跑完」的运行。**

若作业正常完成（`COMPLETED`）**且**期间机器内存水位到过 88%，那它的 `--mem` 就是一个
有效上界 —— memguard 当时真的在查账却没冻它，说明它没超申报。

⚠️ **水位这个条件不能省**：memguard 只在 ≥88% 时查账。机器空闲时跑完，
只说明**没人来查你的账**，不说明你没超申报。拿它当上界会得出偏小的估计，
然后某天机器一忙就被冻，而你会觉得莫名其妙——"上次同样的参数明明跑通了"。

⇒ **查这两个数用一条命令**：`advise.py gpu-peak <jobid>`，它同时给下界、当时水位、
   Slurm 终态，并直接判定上界成不成立。

⇒ **迭代收敛**：第一次不写 `--mem`（拿 96G 兜底）跑完 → 得下界；之后每次往下调一点，
   跑完就把上界收紧，被冻就说明下探过头。几次就夹到一个很紧的区间，
   **而且每次都是有产出的正经活，不是白跑的测试**。

⇒ **被冻结也是信息，别当作废**：它给的是"真实需求 **>** 你当时的申报值"。
   不能拿被冻时的观测值当峰值，但"至少比申报的多"这一条是硬的。

⇒ 要真正准确的峰值，只能让程序自己报（PyTorch：`torch.cuda.max_memory_allocated()`
   —— 它是框架自己记的历史最大值，不采样、不会漏）。但那要求你能改代码；
   上面的夹逼法**不需要动被测程序**，任何工具都适用。

⇒ 无论哪种办法：**该数字只对当前这个输入有效**。换蛋白、换配体规模、换 batch，
   需求就变了，得重测。别把一次的结果当成这个工具的固有属性。

⚠️ **别拿全机聚合外推**：不同工具、不同输入规模的历史作业不是同分布样本，据此定某个作业的
`--mem` 是过度泛化，方向还是危险的那边（报低 = 优先被冻）。全机 P90 只能回答"96G floor 是不是
定高了"这类**策略**问题（管理员的事），不能拿来定你这个作业的 `--mem`。
